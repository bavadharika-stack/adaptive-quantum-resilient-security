# Adaptive Quantum-Resilient Lightweight Security Framework for IoV
### Prototype implementation — ASCON + ML-KEM + ML-DSA + Machine Learning

This folder is a runnable prototype of the research idea in your literature
review: an **adaptive** IoV (Internet of Vehicles) security framework that
uses a Machine Learning model to classify each network message's risk level
(normal / medium / emergency) and then selects the lightest cryptographic
protection that is still safe for that risk level — combining the
NIST-standard lightweight cipher **ASCON** with the NIST post-quantum
standards **ML-KEM** (FIPS 203) and **ML-DSA** (FIPS 204).

## 2. How to run it in VS Code (step by step)

1. **Install Python 3.10+** if you don't have it (check with `python3 --version`
   in a terminal).
2. **Unzip** the project folder and open it in VS Code:
   `File → Open Folder… → proj/`
3. **Open a terminal in VS Code**: `Terminal → New Terminal`.
4. **(Recommended) create a virtual environment:**
   ```bash
   python3 -m venv venv
   source venv/bin/activate        # Windows: venv\Scripts\activate
   ```
5. **Install the dependencies:**
   ```bash
   pip install -r requirements.txt
   ```
6. **Run the whole pipeline with one command:**
   ```bash
   python main.py
   ```
   This will, in order:
   - generate the dataset into `data/iov_security_dataset.csv`
   - train the Random Forest risk classifier and save all evaluation
     plots/metrics into `reports/`
   - run a demo of the adaptive security policy on one normal, one
     medium and one emergency message, printing which crypto was used
     and how long each stage took
   - benchmark ML-KEM/ML-DSA against RSA/ECC and save the
     quantum-resilience evidence report
7. **Check the outputs:** open the `reports/` folder — the `.png` files
   can be viewed directly in VS Code, and the `.json`/`.txt` files can be
   opened as text.

**To re-run just one stage** (e.g. after tweaking the dataset generator):
```bash
python src/generate_dataset.py
python src/train_model.py
python src/adaptive_security.py
python src/benchmark_pqc_vs_classical.py
```

## 4. Answering "is it actually quantum resilient?"

Quantum resistance in cryptography is never demonstrated by literally running
an attack — no such quantum computer exists yet. It is demonstrated by
showing that the scheme's security rests on a **mathematical problem with no
known efficient quantum algorithm**. This prototype backs that claim two ways:

1. **Correctness proof** — `pqc_engine.py` runs the *real*, standards-compliant
   ML-KEM-768 (FIPS 203) and ML-DSA-65 (FIPS 204) reference algorithms
   (via the `kyber-py` / `dilithium-py` libraries, which implement the
   official NIST test vectors), and every round-trip
   (encapsulate → decapsulate, sign → verify) is checked to succeed.
2. **Hardness comparison** — `benchmark_pqc_vs_classical.py` prints, for
   every algorithm used, its underlying hard problem and the best known
   classical *and* quantum attack. RSA/ECC rely on factoring/discrete-log,
   both solved in polynomial time by Shor's algorithm on a
   cryptographically-relevant quantum computer (CRQC) — they are **not**
   quantum resistant. ML-KEM/ML-DSA rely on Module-LWE/Module-SIS lattice
   problems, for which the best known quantum attack (quantum lattice
   sieving) gives only a sub-exponential speed-up — this is precisely why
   NIST selected them as the post-quantum standards, and it is the basis
   for calling the framework "quantum resilient."

Be upfront in your paper (and to your supervisor) that this is an
**algorithmic / standards-compliance argument**, not a live quantum attack —
that is the accepted form of evidence in PQC literature because
fault-tolerant quantum computers capable of running Shor's algorithm at
cryptographic scale do not exist yet to test against.

## 5. Honest limitations to mention in your paper

- The dataset is **synthetically generated but domain-grounded**: feature
  ranges, correlations and the three attack sub-scenarios are built from
  published V2X/VANET parameter ranges, and ~3% label noise + realistic
  class imbalance are injected so the classes are not trivially separable.
  For a stronger paper, validate the classifier against a public VANET/IoV
  intrusion dataset (e.g. VeReMi, CICIoV2024) as future work.
- `kyber-py` / `dilithium-py` are pure-Python reference implementations —
  correct against the FIPS test vectors, but noticeably slower than a
  production C implementation (e.g. `liboqs`), so the latency numbers in
  the benchmark are a conservative *upper bound* on PQC overhead — a
  real embedded/automotive deployment using optimized C/hardware ASCON
  and liboqs would be substantially faster.
- ASCON's 128-bit key gives ~64-bit security under Grover's algorithm;
  the framework mitigates this by deriving short-lived per-session keys
  from ML-KEM rather than reusing a static long-term ASCON key.
